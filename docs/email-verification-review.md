# Подтверждение email через Resend

Сверка на 20 ноября 2026 года. Основания — ТЗ из чата **Analyst**, отчёты **Developer** и **Tester**, текущие файлы backend и ТЗ на локальную приёмку.

**Итог.** Новый парольный аккаунт получает письмо, подтверждает email и входит. Tester прошёл этот сценарий на локальной PostgreSQL с настоящей доставкой через Resend. Итоговый **PASS** относится к функциональной приёмке на локальном окружении. Для полного закрытия ТЗ Analyst остаются отдельные регрессии и проверки параллельности.

| --- | --- |
| Analyst | Зафиксировал сценарий регистрации, срок и лимиты кода, требования к повторной отправке, сохранению доступа существующим пользователям и OAuth. |
| Developer | Подключил Resend, дополнил регистрацию и вход, добавил проверку и перевыпуск кода. Адаптировал подготовку пользователей для теста заявок. Сообщил об успешной сборке и HTTP-проверках с подменой Prisma и Resend. |

В рамках этой сверки проверены исходники, миграция, diff и типизация `tsc --noEmit`. Повторная отправка писем и операции записи в БД не выполнялись.

## Как работает сценарий

### Регистрация

[`auth.routes.ts`](../src/routes/auth.routes.ts) связывает маршруты с [`auth.controller.ts`](../src/controllers/auth.controller.ts). Контроллер проверяет поля запроса. В [`auth.service.ts`](../src/services/auth.service.ts) проверяется уникальность email и username, пароль хешируется bcrypt. Вложенная операция Prisma атомарно создаёт пользователя с `emailVerified = false` и запись кода. Уникальные ограничения БД также защищают от дубликатов при параллельной регистрации.

[`emailVerification.service.ts`](../src/services/emailVerification.service.ts) генерирует строку из шести цифр, включая возможный начальный ноль. В БД записываются HMAC-SHA256 от email и кода с серверным секретом, время выдачи, срок действия и счётчик неверных попыток. После сохранения [`config/email.ts`](../src/config/email.ts) отправляет исходный код через Resend. Если провайдер отклоняет вызов или не отвечает за 10 секунд, аккаунт остаётся созданным и регистрация возвращает `verificationEmailSent: false`.

### Подтверждение и вход

Код действует **10 минут** и допускает **5 неверных попыток**. Сервис блокирует строку неподтверждённого парольного пользователя в транзакции PostgreSQL. Неверный код увеличивает счётчик, а HTTP-ошибка возвращается после фиксации транзакции. Правильный код выставляет `emailVerified = true` и удаляет запись кода в той же транзакции. Это делает код одноразовым и согласует подтверждение с параллельным перевыпуском.

Вход сначала проверяет пароль. При правильном пароле и неподтверждённом email он возвращает `403 EMAIL_NOT_VERIFIED`. Передача поля `code` в JSON ошибки проходит через [`AppError.ts`](../src/utils/AppError.ts) и [`errorHandler.ts`](../src/middlewares/errorHandler.ts). Успешный вход выдаёт JWT на семь дней. OAuth идёт через прежний внутренний маршрут и не использует эту проверку. Поэтому `emailVerified` в текущем контракте нельзя использовать как универсальный признак того, что вошедшего через OAuth пользователя нужно отправить на экран кода.

### Повторная отправка

Контроллер пропускает к сервису до **5 запросов за 60 секунд на IP** в одном процессе Express. В БД сервис проверяет, что с момента предыдущей выдачи кода для аккаунта прошло **60 секунд**. Если можно перевыпустить код, сервис заменяет хеш, обновляет время выдачи и срок, сбрасывает счётчик и после транзакции вызывает Resend. Предыдущий код перестаёт действовать уже при замене записи. Если письмо не отправилось, следующий перевыпуск станет доступен по истечении интервала.

Для неизвестного email, подтверждённого аккаунта и сработавшего лимита штатный ответ тот же `202`. Это выравнивает HTTP-статус и тело. По коду видно, что при фактической отправке сервер ждёт Resend, поэтому одинаковое время ответа не гарантировано.

### Хранение и миграция

[`schema.prisma`](../prisma/schema.prisma) определяет одну запись `EmailVerificationCode` на пользователя с каскадным удалением при удалении пользователя. [Миграция](../prisma/migrations/20261118115121_email_verification/migration.sql) добавляет поле и таблицу и выполняет backfill `emailVerified = true` для всех существовавших на момент применения пользователей. Это сохраняет доступ старым парольным аккаунтам. Backfill не подтверждает фактическую доставку писем на их адреса.

## Что передать фронтендеру

Передай базовый URL backend для нужного окружения и следующий контракт.

| Запрос | Что сделать на клиенте |
| --- | --- |
| `POST /api/auth/register` с `email`, `username`, `password` и необязательным `locationId` | На `201` открыть экран ввода кода и передать туда email. Если `verificationEmailSent: false`, сообщить, что аккаунт создан, и предложить повторную отправку. |
| `POST /api/auth/verify-email` с `{ email, code }` | Передать код строкой из шести цифр. На `204` перейти к входу. У `204` пустое тело. При `400` показать текст ошибки и дать исправить ввод или запросить новый код. |
| `POST /api/auth/resend-verification` с `{ email }` | Показать нейтральное сообщение «Если отправка доступна, письмо придёт на указанный адрес». `202` с `{ "status": "Accepted" }` не сообщает о доставке. Поставить клиентский таймер на 60 секунд для кнопки. |
| `POST /api/auth/login` с `{ email, password }` | На `403` и `code: "EMAIL_NOT_VERIFIED"` открыть экран подтверждения. `401` обработать как неверные данные входа. При `200` использовать существующий поток с `{ token, user }`. |

Проверить в интерфейсе ведущий ноль, повторную отправку после закрытия экрана и регистрацию, при которой письмо не принято провайдером. Сценарий OAuth оставить на существующем маршруте. Изменения фронтенда и его сквозной прогон в этой сверке не проверялись.

## Что передать DevOps

1. **Серверное окружение.** Задать `RESEND_API_KEY` с правом **Sending access** для подтверждённого домена, `EMAIL_FROM=no-reply@itteamplatform.ru` и отдельный случайный `EMAIL_VERIFICATION_SECRET`. На всех репликах одного окружения нужен одинаковый секрет. При его замене выданные коды перестанут проходить проверку. Передавать значения через хранилище секретов или настройки backend. `.env.example` пока не перечисляет эти три переменные.
2. **Очередность выкладки.** Сверить целевую БД и `npx prisma migrate status`. Применить миграции командой `npx prisma migrate deploy` до запуска версии кода, использующей новые поля. Для сборки сгенерировать Prisma Client из текущей схемы через `npx prisma generate`, затем выполнить `npm run build`. Согласовать выкладку фронтенда с новым `403` при входе.
3. **Прокси и несколько реплик.** Лимит по IP сейчас использует `req.ip` и память одного процесса. В `app.ts` нет настройки `trust proxy`. Перед выкладкой за reverse proxy проверить, какой IP видит Express, и при необходимости согласовать настройку доверенных прокси. Общий лимит между репликами потребует отдельной реализации или ограничения на уровне инфраструктуры. Интервал по аккаунту уже хранится в общей БД.
4. **Проверка после выкладки.** Проверить `/api/health`, затем на контролируемом ящике пройти регистрацию, доставку, подтверждение и вход. При сбое отправки смотреть журнал Resend: backend пишет общее предупреждение без содержимого письма.

Для фронтенда контракт можно передавать сейчас. Перед релизом отдельно закрыть регрессию старого парольного аккаунта, OAuth и заявок, а также проверить параллельное подтверждение и работу лимита по IP в целевой схеме развёртывания.
